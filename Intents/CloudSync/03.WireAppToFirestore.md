# 3. WireAppToFirestore

**Goal**: Refactor `app.js`'s task CRUD from synchronous `localStorage` mutation to Firestore via `tasks-repo.js`, driven by a real-time subscription.
**Est.**: 1.5h
**Dependencies**: TaskRepository

## Steps
- [ ] Convert `app.js` to an ES module (`<script type="module" src="js/app.js">` in `index.html`) so it can `import` from `tasks-repo.js` and `firebase.js`
- [ ] Remove `loadTasks()` / `saveTasks()` (`localStorage`-based) and the `tasksByDate` variable's role as the write target; instead, subscribe once a user is confirmed (`onAuthStateChanged`) via `subscribeToTasks(uid, tasks => { tasksByDate = groupByDate(tasks); renderWeekStrip(); renderDayDetail(); })`
- [ ] Add a `groupByDate(tasksArray)` helper that turns the flat array from Firestore back into the `{ [dateKey]: task[] }` shape the render functions already expect, so `renderWeekStrip`/`renderDayDetail`/`sortedTasks` need no changes
- [ ] Replace the direct mutations in the checkbox-change handler, delete-button handler, and the add/edit form submit handler with calls to `updateTask` / `deleteTask` / `addTask` respectively — no local mutation or manual re-render needed since the `onSnapshot` subscription re-renders automatically
- [ ] Unsubscribe the previous listener if one exists before starting a new one (defensive, in case auth state changes more than once in a session)

## Definition of Done
- [ ] Adding, editing, completing, and deleting a task all go through `tasks-repo.js` — no direct Firestore or `localStorage` calls left in `app.js`
- [ ] The UI updates when Firestore data changes, whether that change came from this tab or was pushed by the subscription
- [ ] No regression in what intent 4 of DailyPlanner already verified (add/edit/cancel/validation), other than persistence now being Firestore instead of `localStorage`
